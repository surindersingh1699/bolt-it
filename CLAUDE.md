# CLAUDE.md — Bolt-it

Read at the start of every session in this directory.

## Guidelines

- Only add code that directly adds functionality. No empty scaffolding, no placeholder files.
- Build step by step so the developer fully understands each part while it is being built.
- Prefer deleting code over adding abstraction.

## main — how it actually works

- **Orchestration:** [src/lib/ticket-graph.ts](src/lib/ticket-graph.ts) — a `@langchain/langgraph` `StateGraph` run in-process (no LangGraph Platform). `MemorySaver` checkpointer is a `globalThis` singleton. Thirteen nodes: observe → strategist ⇄ operator ⇄ intentValidator → reviewSteps → execute, plus researcher, the two approval nodes, the two ladder-check nodes, finalize and humanHandoff. **Roles, not tiers** — see [docs/ROLES.md](docs/ROLES.md).
- **A dead run escalates, never strands.** Graph entry points run through `runGuarded` ([ticket-graph.ts](src/lib/ticket-graph.ts)): a thrown run escalates the ticket with a note and tells the employee. `sweepOrphanedTickets` (called from `/api/state`, throttled) escalates `new`/`drafting`/`executing` rows with no live in-process run — MemorySaver dies with the process, so those rows can never resume on their own. `awaiting_approval`/`awaiting_confirmation` are waiting on a person and are left alone.
- **Two models, deliberately asymmetric.** [strategist.ts](src/lib/strategist.ts) is opus and called rarely: it reads the problem, the screenshot and the machine's readings, diagnoses, and *authorises* actions. [operator.ts](src/lib/operator.ts) is sonnet and called often: it binds real app names and paths, retries what fails mechanically, runs extra reads to get unstuck, and hands back when done or blocked. Most of a ticket's rounds are mechanical, which is the entire cost argument. Bounds: `MAX_STRATEGY_ROUNDS=3` (opus), `MAX_OPERATOR_ROUNDS=3` per strategy (sonnet).
- **The operator cannot author a change.** `authorizeOperatorSteps` ([operator.ts](src/lib/operator.ts)) lets it run any READ freely and only the WRITES the strategist authorised — matched on capability, so correcting an app name is fine and introducing a different fix is not. In code, never in a prompt, because a prompt can be argued with by a ticket body. An overreach sets `blocked` rather than being dropped silently.
- **A step refused for what it IS is spent, and the code enforces it.** `SpentStep` ([operator.ts](src/lib/operator.ts)) — a `capability` + `params` pair that already ended in `capability_missing` or `policy_block` cannot be dispatched again on that ticket. Checked **before** the read-only fast path, because the step this exists to stop is itself a read: checked after "reads are always allowed", it sails through every round, which is exactly what happened. Params compared by value with sorted keys; the same capability with different arguments still runs, because the refusal was about the binary, not about reading command output. A round left with nothing but repeats sets `blocked` — only the strategist can pick a different observation. Only those two failure kinds count: a timeout or a wrong app name is mechanical and retrying it is the operator's job.
- **Fixes are a ladder, not a batch.** The pending queue is ordered by [ladder.ts](src/lib/ladder.ts) — reads first, then changes cheapest-to-be-wrong-about first — and `runNextStep` runs **at most one change per pass**. A change that lands parks the run on a `interrupt()` and asks the employee whether it worked (`askEmployeeToVerify` → `awaitEmployeeVerdict`, desk moment `rungCheck`); "still broken" resumes onto the next candidate for **zero** model calls, because the run is paused rather than finished. Cost is derived from the `CapabilitySpec` (`risk`, `reversible`, `blastRadius`, `requiresElevation`) and never proposed by a model; the strategist contributes only `likelihood`, which breaks ties **inside** a cost tier and can never promote an irreversible fix over a reversible one. A missing `probe` is a tiebreak, not a cost — `fix.flush_dns` has none on purpose. A fix that came back FAILED or NO EFFECT is spent without asking anyone. Climbing does **not** spend `MAX_REOPENS`: a reopen still means the ticket finished and they came back.
- **The rule that holds the gate up:** models emit data, the graph emits control flow. No LLM returns a `goto`. A supervisor-agent pattern would let a model route around `markAwaitingApproval`, which is why this system does not use one.
- **Resolution is claimed, then checked.** [resolution.ts](src/lib/resolution.ts) refuses `resolved: true` when nothing ran or when everything failed. It replaced running the verifier on a separate model and is stronger — an `if` cannot be talked out of its position. Not "must have a VERIFIED CHANGE": a question ticket is resolved by a read.
- **The service desk is one voice.** [src/lib/desk.ts](src/lib/desk.ts) — `COMMUNICATOR_PROMPT` plus a moment instruction (`intake` / `working` / `heartbeat` / `resolution` / `handoff` / `chat`) is every message the employee ever reads. There were three writers; they drifted, the honesty rules only lived in one of them, and the thinnest owned chat — the only conversation the employee can actually have. **Do not add a second prompt for a new kind of message; add a moment.** Two rules in there work as a pair and must stay paired: `PROGRESSIVE DISCLOSURE` (plain English by default, mechanics held back) and the direct-question rule (they asked, so give the exact value). Delete one and the other means something it was never meant to. `desk.test.ts` asserts both.
- **`awaiting_confirmation` means two things now.** Either the ladder is paused on "did that fix it?" (a fix landed, candidates are still queued) or the ticket genuinely finished. The status cannot tell them apart, so the *message* must — that is why `rungCheck` exists and why it must never be written as a `resolution`. `answerRungVerdict` routes the employee's answer into the paused run and returns `false` when there is nothing paused, at which point the caller falls back to a real reopen.
- **`awaiting_confirmation` is not terminal.** "Still broken" reopens the ticket through `reopenTicketGraph` on the same `thread_id` — history carries, `observe` re-reads the machine, round budget resets. Bounded by `MAX_REOPENS` (1), enforced at the top of the strategist. The bound lives in exactly one place; do not add a second copy in a Server Action.
- **Observation before diagnosis:** [src/lib/observe.ts](src/lib/observe.ts) runs a read-only `diag.*` bundle on the START edge, so the strategist reasons against readings instead of spending a round acquiring them. Whole bundle enqueued before anything is awaited — one agent poll cycle, not one per probe. No device or no heartbeat returns `collected: false` immediately, verbatim into the prompt. The bundle must stay read-only: it runs with no reviewer and no gate.
- **Screenshots:** attached on the ticket, uploaded to the private `ticket-attachments` bucket **before** the row is inserted (the graph starts from `after()`, so uploading later races the first read), fetched server-side as a base64 data URI, and sent to the strategist on round 1 only. [attachments.ts](src/lib/attachments.ts). Do not make that bucket public.
- **Server Actions:** [src/app/actions/tickets.ts](src/app/actions/tickets.ts) — thin wrappers around `graph.invoke(...)` and `graph.invoke(new Command({resume}), ...)`. No business logic here.
- **Intent validation:** [src/lib/intent.ts](src/lib/intent.ts) — a graph node between `operator` and `reviewSteps`, and the only stage that sees the plan **as a whole**. Every other gate rules on one step at a time, which cannot catch four risk-0 reads that together sweep an employee's disk for credentials. Three gates: a query denylist checked **before any model call** (the cheap floor — normalization raises the cost of evasion, it does not close it), a responsiveness check against the reported symptom (**the real backstop**, because it reasons about fit rather than spelling), and a search breadth/budget cap. A denylist hit is `policy_block` → `humanHandoff`, never a silent drop.
- **Risk gate:** [src/lib/reviewer.ts](src/lib/reviewer.ts) — an LLM reviewer rules on every step: `allow` / `ask_human` / `block` / `needs_evidence`. Under `AUTONOMY=full`, `needs_evidence` does not hard-refuse execution. Three things remain un-bypassed: `block` (prompt injection / unrelated step), unknown capability, and expired/over-risk temporary grants.
- **Policy decides; the reviewer only reports.** [src/lib/policy.ts](src/lib/policy.ts) is a pure, I/O-free `decide()` — the whole policy is a truth table. Under `AUTONOMY=full`, human approval rules (`persistent-change`, `irreversible-elevated`, `intent-unexplained`, `reviewer-unavailable`) are auto-approved.
- **Autonomy is a rung ladder:** `simulation` → `shadow` → `limited` → `gated` → `full` ([autonomy.ts](src/lib/autonomy.ts)). Default is `full` across all environments (`AUTONOMY=full`).
- **Capabilities are data.** One `CapabilitySpec` record per capability in [capabilities/registry.ts](src/lib/capabilities/registry.ts): `risk` 0-4, `os`, `requiresElevation`, a zod `params` schema, `command`, `probe`, `rollback`, `reversible`, `blastRadius`, and **provenance** (`source: built-in | approved_pr | temporary`, `version`, `author`, `approvedBy`, `expiresAt`). `risk === 0` **is** read-only — derived, never a second hand-maintained list. A param that fails its schema fails the step instead of being coerced into a different action. `registry.test.ts` enforces completeness, and that test is the mechanism behind "no capability bypasses the substrate". Never add a capability by editing a branch — add a record.
- **Memory is UNWIRED, on purpose.** `user_memory` and `incident_memory` still have their modules, tables and tests; nothing calls them. They come back once the loop is proven on real tickets. Do not delete them, and do not re-wire them without asking.
- **Researcher:** [src/lib/research.ts](src/lib/research.ts) is a graph node and the **quarantine boundary** for external text. Raw pages enter the distiller and never leave it; out come at most 5 one-sentence claims, each attributed to a URL actually retrieved that round. A `ResearchFinding` has no field that can carry a command or a capability id. Unattributable claims are dropped; no distiller means nothing is admitted; text addressed to the reader comes back as a `flag` and lands in the findings. The strategist asks, bounded at `MAX_RESEARCH_ROUNDS = 2`. [knowledge.ts](src/lib/integrations/knowledge.ts) is transport only — never wire it to a prompt directly.
- **Research seeds the ladder, and the planner names the action.** The strategist's recommended opening move on a recognisable symptom is a *remediation* question — "known fixes for YouTube not loading in Chrome on Windows 11" — which returns the same list a technician would find by searching. **The source supplies knowledge; the strategist supplies the capability id.** That split is what keeps the quarantine intact: `research.ts` is unchanged, a `ResearchFinding` still cannot carry a command or a capability id, and a described fix with no matching capability becomes a `capability_request` rather than a near-miss. A research round deliberately **does not spend a strategist look** — charging it one punished the tickets that followed the advice; `MAX_RESEARCH_ROUNDS` is the bound instead, so the worst case is `MAX_STRATEGY_ROUNDS + 2` opus calls.
- **How much evidence a change needs depends on what being wrong costs.** A cheap self-reversible fix needs only a plausible link to the symptom — it is tried alone and the employee is asked straight after, so being wrong costs a minute. An irreversible, elevated or directory-touching fix still must follow from something observed. These two rules are a **pair**: delete the first and tickets go back to reading for three rounds and reaching a person having changed nothing; delete the second and "try the cheap thing on a hunch" becomes "reset their password on a hunch". `strategist.test.ts` asserts both.
- **Data:** [src/lib/data.ts](src/lib/data.ts) is the access layer — InsForge primary, in-memory [src/lib/db.ts](src/lib/db.ts) as fallback. **Collapsing to InsForge-only is the next planned change**; new tables (e.g. `user_memory`) are already written InsForge-only, with no in-memory mirror.
- **Step kinds:** `device` (local agent), `backend` (directory/AD in our own store), `reply` (message to the user). Nothing else — and deliberately no `knowledge` kind: a web lookup touches no company system, so charging it a plan slot, a safety review and an approval decision bought nothing. HOW each runs lives in the executor registry ([src/lib/executors.ts](src/lib/executors.ts)), not in the graph — a new execution surface (SSH, Intune, SCCM) is a new executor plus a registry entry, and never an edit to `ticket-graph.ts`. Slack OAuth, the demo-workspace flow, and the Okta/MDM/Aside/Tensorlake adapters were deleted — they narrated work that never happened.
- **Device execution:** [scripts/local-agent.mjs](scripts/local-agent.mjs) polls for jobs and runs an allowlisted command set on a real machine (macOS + Windows). Every job is probe → act → probe → **rollback if the change did not take**; the before/after diff is the only thing that counts as success, and the effect diff is computed over the pre-rollback probes so a successful restore never reads as a change. **One token per device**: jobs carry a `deviceId` and are only ever handed to that machine ([device-auth.ts](src/lib/device-auth.ts)); the shared token survives only behind `ALLOW_SHARED_AGENT_TOKEN=1`. Copy the file to the machine by hand — there is no self-update and no `public/setup.ps1`. The runtime (token check + poll loop) is guarded behind `IS_ENTRYPOINT`, so `executeJob` and the handler table can be imported by a test harness with no server. Write handlers today: `restart_app`, `clear_app_cache`, `toggle_wifi`, `set_dns_servers`, `flush_dns`, `restart_service`, `clear_print_queue`, `renew_dhcp_lease`, `gpupdate`, `set_proxy`, `reset_winsock`, `restart_shell`, `set_taskbar_autohide`, `kill_process`, `set_startup_item`, `install_package`, `enable_device`, `reconnect_vpn` (add one by registering it in `HANDLERS` with an `expectsChange` flag, a probe and — where a real undo exists — a `rollback`; never a bare shell call). **The rollback transaction does not fire when the act itself reported failure** — an act that says it failed, next to probes that agree nothing moved, has nothing to reverse, and running the undo anyway makes an unauthorised change whose error then replaces the real reason on the ticket. Reads add `fs_find`, `screenshot`, `vpn_state` and `http_check` — the last of these uses the agent's own resolver and `fetch` rather than a binary, because `curl` is deliberately on neither allowlist, and it reports resolution and connection as separate facts while never returning a byte of the response body. **Redaction** lives in [scripts/redact.mjs](scripts/redact.mjs), is applied to the whole payload on the way out, and again server-side after parsing.
- **The footprint has to be visible without going to look for it.** [scripts/vm/agent-tray.ps1](scripts/vm/agent-tray.ps1) is a WinForms tray app — blue icon while a job runs, balloon naming it, a window listing everything that ran on the machine today (reads included) with its verdict, and pause/resume. It reads the agent's loopback console and the journal; it can never run a device command. Served from `/api/agent/tray` and re-pulled by the same supervisor loop as the agent, so it converges on the current build. Zero dependencies, deliberately: an Electron app would be a new dep and a build step on the demo VM.
- **Fingerprints:** every state-changing job writes three records on the machine before upload — the append-only journal (`~/.bolt-it/journal`), a change record with the **exact undo command** (`~/.bolt-it/changes/<ticketId>.jsonl`, via `recordChange`), and a line in the OS's own log (Windows Application event log source `BoltIt`; macOS `~/Library/Logs/bolt-it.log`, via `writeSystemLog`). The revert command and change-record path ride back on the envelope, so `formatProofLines` documents them on the ticket. A read or a `no_effect` run writes no change record — there is nothing to undo.
- **Proof of effect:** [src/lib/evidence.ts](src/lib/evidence.ts) — `deriveJobStatus` turns the device's envelope into `succeeded` / `no_effect` / `failed`. `no_effect` means the commands ran and the machine did not change; it fails the step. `formatProofLines` renders the envelope as the audit block on the step, including **the exact command each probe used** — a summary is a claim, a command someone can paste into a terminal on the same machine is evidence.
- **Proof has to be visible, or it is not proof.** [Evidence.tsx](src/app/components/Evidence.tsx) renders the envelopes: every probe with the command that read it, the field-level before → after diff, every argv with its exit code and full stdout, the rollback outcome, and the journal / change-record / undo paths on the machine. Served on demand by [/api/evidence/[ticketId]](src/app/api/evidence/[ticketId]/route.ts) — **never on `/api/state`**, which polls every 600ms and would carry ~100 KB of stdout per job for a panel that is closed almost all the time. Two surfaces, one component: collapsed inside the staff ticket's `Technical detail`, and full-width at `/audit/<ticketId>` for showing someone. The redaction caveats are rendered on the page, not hidden — anyone who compares this against the machine will hit them.
- **The registry's claims are checked against the agent's build.** `probe: "probeDns"` and `rollback: "…"` are strings about a *different file*, and nothing verified them: three capabilities advertised undos `HANDLERS` did not have, so `executeJob`'s rollback transaction — gated on `handler.rollback` — never fired, while `ladder.ts` went on ordering them by a reversibility the build could not deliver. [probe-binding.test.ts](src/lib/capabilities/probe-binding.test.ts) imports the real agent module and asserts both directions of `probe`, `expectsChange` and `rollback` per capability. Change one side without the other and the suite goes red.
- **The device says what it can do; we never assume it.** Every agent publishes its `surface` on the heartbeat — the job handlers its build implements and its two binary lists (`default`, `grantable`) ([local-agent.mjs](scripts/local-agent.mjs) `describeSurface`). `unsupportedByDevice` ([executors.ts](src/lib/executors.ts)) checks a step against it **before dispatch**, and `surfaceAsContext` ([observe.ts](src/lib/observe.ts)) puts the same lists in the planner prompts. The registry says what the SYSTEM can do; the surface says what THAT MACHINE can do, and the gap between them is what cost T-4935 three looks. **A new binary or handler is a record in the agent's table and nothing else** — the server, the prompts and the failure taxonomy pick it up from the heartbeat.
- **One build per fleet, enforced at the door.** The jobs route hands work only to an agent whose `x-agent-build` is the build being served (or `dev`, a hand-run copy). An agent too old to report one gets nothing and is told why; it self-exits and the supervisor pulls the current bundle. Two agents on one machine — a scheduled task plus a hand-started old copy — is what made the same read succeed and fail minutes apart.
- **A refused read is a decision, not a dead end.** [scripts/local-agent.mjs](scripts/local-agent.mjs) has a second closed list, `GRANTABLE_BINARIES` — read-only binaries that are off by default and that a named technician can switch on for **one ticket** through the existing `interrupt()` gate. The agent marks such a refusal `GRANTABLE:<binary>:`, `grantableBinaryFrom` ([executors.ts](src/lib/executors.ts)) turns it into a `capability_missing` failure, and `runNextStep` routes it through `decideGrant` ([grants.ts](src/lib/grants.ts)) instead of burning a strategist round. **Who decides is the autonomy rung, and it lives in one place:** at `AUTONOMY=full` the graph grants the binary itself and retries the step (an unattended queue has no technician to click); every rung below keeps the `interrupt()`. Only a failure carrying `grantableBinary` is grantable — a missing handler is not, because a grant would retry it into the same wall forever. **This is not a run-anything path and must never become one:** a grant only widens WHICH binary may run, the binary must still be on the grantable list, and every subcommand and argument filter still applies — `dscacheutil -flushcache` is refused with the grant held. Grants live on the ticket (`Ticket.grantedBinaries`) and ride to the device on the job, never in the command string, so nothing a model composes can forge one.
- **Failure taxonomy:** every step that reaches `status: "failed"` also carries `failure: { kind, detail }` (`StepFailureKind` in [types.ts](src/lib/types.ts)). A bare `failed` is not acceptable — a refused step, an offline agent and a fix that landed on an unchanged machine are three different problems with three different owners. A failed step routes through `humanHandoff` so the artifact is written.
- **Memory:** [src/lib/memory.ts](src/lib/memory.ts) + `user_memory` table — keyed facts (nickname, office, device) and one episode per ticket, written by the LLM extractor at finalize, read at draft time. No external memory service.
- **Model calls:** every call goes through `gatewayChat` in [src/lib/integrations/gateway.ts](src/lib/integrations/gateway.ts) — one place for transport, timeout, failure shape and token accounting. It returns `string | null`; null always means "no usable answer", which is what lets callers fail closed with one check. Never add a bare `fetch` to a model endpoint.
- **Cost:** [src/lib/usage.ts](src/lib/usage.ts) records tokens, latency and success per call per ticket, surfaced at `/api/state` and in the metrics view. Tokens only — no price table, because rates move per account and a stale one would be believed.
- **Realtime:** client polls `/api/state` every 600ms ([StateProvider.tsx](src/app/components/StateProvider.tsx)). Do not poll faster.

## Rules

1. **Typecheck must pass.** `pnpm typecheck` is the gate. It is currently clean — keep it that way.
2. **Approval gate is structural.** The human gate is a LangGraph `interrupt()`, resumed with `Command({resume})`. Never add a code path that reaches a high-risk step without it.
3. **Capability-scoped actions only.** No general-purpose "run anything" tool. A new action gets a named capability in [capabilities.ts](src/lib/capabilities.ts) and a place on the read-only or changes-something side of that list. Getting the side wrong in the permissive direction lets the cheap model author it.
4. **Adapters never throw.** Catch and return `{ ok: false, log: [...] }`. A failed step escalates the ticket; it never crashes the app.
5. **No adapter without a real backend.** If a capability cannot really be performed, it does not exist — do not add a narrated stand-in. A device job that changes nothing is `no_effect` and can never justify a "resolved" verdict.
6. **Components never write to the store.** Component → Server Action → `data.ts`.
7. **No new deps without asking.** pnpm only — never npm or yarn. The lockfile is committed.
8. **Icons:** `lucide-react` only. **Validation:** `zod`, already installed.
9. **No demo special-casing in production paths.** Do not branch on ticket text or reporter email to force a canned result.
